### 🧬 Data Model Update Task Template (Drafted v14)

> _ICDC provenance: this template mirrors CTDC's Data Model Update Task template, filled with ICDC info. The split between the two ICDC modeling templates is by **driver** — study submission vs. internal ICDC project — **not** by size. Canonical example is TBD: the first ICDC ticket drafted under this template becomes canonical. The DM Federal Lead is Heather Creasy._

> **Use this template for every ICDC data model change to `CBIIT/icdc-model-tool` that is driven internally — by the ICDC project itself — rather than by an incoming study submission.** That spans the full weight range: a lightweight additive change (new optional properties or enum values requested by the ICDC application roadmap, e.g. Program/Portfolio curation fields) *and* a heavyweight infrastructure change (breaking MAJOR-version schema changes, model framework upgrades, cross-cutting multi-repo refactors). The distinguishing factor is the **driver**, not the weight. **Study-driven** changes — properties, enums, or permissible values requested by a study submission — use the **Data Modeling for Study Submission** template instead. As of v11 the two modeling templates share an identical shape except for the study-submission template's ⭐ Data Concierge section; they differ only in context (internal vs. study workbook, internal driver vs. study submission). Like the other data management templates, this one moves through Dev → QA → Stage → Prod, but the mechanism is the **Data Model Contribution** process — a git feature branch → PR into `develop` (Dev and QA) → PR into `master` (Stage and Prod) and tag/release — **not** a data-loading pipeline. It is validated against schema state and the Data Model Navigator, and propagates downstream to the CRDC Data Hub via the release tag `[ICDC-VERIFY — confirm whether ICDC's model syncs downstream to crdc-datahub-models]`. The branch-and-release flow follows the ICDC data-model contribution process `[ICDC-VERIFY — confirm ICDC's data-model contribution SOP/process]`, which is authoritative; this ticket tracks the work through its Jira states, not the procedure itself.

**The governing rule: every model change has a CDE Request Workbook**

There is no "no workbook" path for an ICDC data model change. Every change — additive or breaking, study-driven or internal — records its changes and CDE assignments in a CDE Request Workbook. There are exactly two kinds of workbook, and the **driver** of the change selects which one:

- **Study-specific workbook** — owned by the Data Concierge handling that study. Used by study-driven changes (the Data Modeling for Study Submission template).
- **Internal ICDC workbook** — the single persistent **ICDC Internal CDE Request Workbook**, which belongs to the **ICDC project itself with no individual owner**. Used by internally-driven changes (this template).

This rule is the reason the split between the two modeling templates is drawn on the driver: *who drives the change decides which workbook holds the term-level truth.* An internally-driven change records in the internal workbook even when it is a single optional property; a study-driven change records in that study's workbook even when it is small.

**The ticket is a milestone tracker, not a term inventory**

This template is deliberately lean. The CDE Request Workbook is the term-level source of truth — per-property CDE bindings, caDSR coordination status, permissible-value decisions, the full list of nodes and properties touched, and how many of each. The ticket does **not** duplicate any of that. It carries the workbook pointer, the SemVer/version milestones, the branch-and-release signoff, and the Jira links to related work. If a field would name a specific property, permissible value, enum value, relationship, or CDE code — or count how many are changing — it belongs in the workbook, not the ticket.

**Why this template**

The ICDC team's data management function has two sub-functions, and the modeling sub-function splits into two work patterns by driver:

- **Loading data** — taking a CRDC submission's *contents* (study metadata, files, IndexD entries) into ICDC's databases. Tracked with the Data Loading Task template and, upstream, the IndexD Registration Task template.
- **Modeling data** — changing the *shape* of what ICDC's databases can hold. Two work patterns:
  - **Study-driven model changes** — requested by an incoming study submission, anchored on that study's CDE Request Workbook. Tracked with the Data Modeling for Study Submission template.
  - **Internally / ICDC-driven model changes** — initiated by the ICDC project itself (the application roadmap or the data team), anchored on the internal CDE Request Workbook. Tracked with **this** template, across the full additive-to-breaking weight range.

The boundary between the two modeling templates is *who's driving the change*. A study coming to ICDC with their workbook is study-submission modeling (the Data Modeling for Study Submission template). An internal decision — to add curation properties for a new application page, to restructure how cases link to studies, or to upgrade the underlying Bento MDF framework — is an internally-driven Model Update Task (this template), and records in the internal workbook regardless of how light or heavy it is.

A model update covered by this template is a single end-to-end change that follows the ICDC data-model contribution process `[ICDC-VERIFY — confirm ICDC's data-model contribution SOP/process]`: confirm the CDE Request Workbook and any caDSR/ServiceNow coordination, create a feature branch off `develop`, edit the `model-desc/` YAML files together, update the model version-history file `[ICDC-VERIFY — confirm the ICDC model version-history file]`, bump the YAML `Version:` field, commit and push, open a PR into `develop`, validate on Dev/QA, then PR `develop` into `master` (Stage and Prod) and tag/release, verifying the YAML `Version:` matches the planned tag and publishing GitHub Release notes, then verify the downstream sync `[ICDC-VERIFY — confirm whether ICDC's model syncs downstream to crdc-datahub-models]`. It is one piece of work in one ticket; related tickets are carried by native Jira issue links. A data-loading Jenkins pipeline is **not** part of this — that runs only if existing data must be re-loaded under the new schema, which is a separate Data Loading Task (the Data Loading Task template).

The canonical procedural reference for *how* model changes are designed, branched, committed, reviewed, tagged, and synced downstream is the ICDC data-model contribution process `[ICDC-VERIFY — confirm ICDC's data-model contribution SOP/process]`. The CDE-coordination steps (the ServiceNow request to caDSR for new or updated CDEs/PVs, and the DM Federal Lead & Subject Matter Expertise Review with its DHDM Jira Issue) derive from the NCI Data Hub **"DM Updates" Kanban SOP**. This Jira template does **not** duplicate either SOP — it tracks the model change as a ticket and points at the SOPs for procedural detail. If anything in this template appears to conflict with a SOP, the SOP is authoritative. (Note: the DM Updates Kanban *lane lifecycle* — DH Coordinator hand-offs, Pending-Condition-Cleared, Active Submission, the validation loop — is submission-scoped and applies to study-submission modeling work, not to internally-driven Model Update Task work, which has no submitter and no active submission. The caDSR/ServiceNow request and the DM Federal Lead & Subject Matter Expertise Review, however, are universal and are reflected in Section 3 below.)

The most common antipatterns we've seen on model update tickets:

1. **Treating an internal change as "no workbook."** Every model change records in a CDE Request Workbook. An internally-driven change records in the internal ICDC workbook — there is no path where a model change skips the workbook. (This is the classic first-pilot miss: filing a change asserting "no CDE Request Workbook" and "no caDSR CDE binding" before CDEs turn out to be required.)
2. **Routing by weight instead of driver.** The split between the two modeling templates is *who drives the change*, not how heavy it is. A study-driven change is study-submission modeling even if it is tiny; an internally-driven change is a Model Update Task even if it is a single optional property. Don't send a lightweight internal addition to the Data Modeling for Study Submission template just because it "feels study-sized" — it has no study and no study workbook, so it belongs here, recorded in the internal workbook.
3. **Duplicating term-level detail into the ticket.** Listing the specific properties, permissible values, enum values, relationships, or caDSR CDE codes — or counting how many of each are changing — duplicates the workbook and drifts out of sync. Name the workbook (Section 2); keep the per-term inventory and the tallies there. The ticket records the work, not terms or counts.
4. **One ticket per affected repo.** Splits a single model change across the `icdc-model-tool` ticket, the dataloader ticket, and the frontend ticket, with manual cross-linking. A model change is one end-to-end unit; the multi-repo touch is implementation detail. Track it within the one ticket and with native Jira issue links, not as separate tickets that lose the connection to the model change.
5. **Treating schema changes as software development.** Schema changes generate code work (loader updates, frontend renderers), but the *concern* is data shape — what nodes exist, what properties they carry, what relationships connect them. That is data management. The cascading code work is owned by the data management ticket, not split out as standalone software development tickets that lose the connection to the model change.
6. **Restating the SOP procedure or the version inside the ticket.** A step-by-step promotion procedure — or a SemVer classification, target version, or schema-artifact checklist — in the description duplicates the ICDC data-model contribution process `[ICDC-VERIFY — confirm ICDC's data-model contribution SOP/process]`, which is authoritative, and GitHub, which already records the version (the YAML `Version:` field, the git tag, the GitHub Release). The contribution process describes *how* to edit, version, tag, and sync; GitHub holds the version; the ticket carries the *work* through its Jira states. Don't reproduce any of that in the description. (The Section 4 Steps to Completion spine is fine — it names each phase and points at the process, rather than reproducing the procedure.)
7. **Skipping the DM Federal Lead & Subject Matter Expertise Review.** The review is required on **every** model change, not just those with new CDEs/PVs. The DHDM Jira Issue is filed first (Section 3, row 2) and tracks the review; the caDSR II Help Desk Request Form is filed and its link is added to row 3 once it exists. The review gates promotion to `master` (Stage and Prod). It is not optional even for additive internal changes; when no new CDEs/PVs are involved, the caDSR II Help Desk Request Form row simply stays empty and the DM Federal Lead is instead added as a watcher on the Jira issue.

The template below resolves these with three commitments:

1. **Every change has a workbook, and a review gate.** Section 2 anchors the change to its CDE Request Workbook — the internal ICDC workbook for this template's internally-driven scope. Section 3 captures the DM Federal Lead & Subject Matter Expertise Review (the DHDM Jira Issue first, then the caDSR II Help Desk Request Form) on every change. The workbook is the term-level source of truth; the ticket carries the work.
2. **One Task per end-to-end model update.** A single concern from initial schema edit through Prod validation and downstream verification — not one ticket per repo. The ticket's Jira status reflects the current state; the branch/release progress lives in those states and in GitHub, not in a description table.
3. **Procedure and versioning live in the contribution process and GitHub, not the ticket.** How the model is edited, branched, versioned, tagged, and synced — and which SemVer level applies — is governed by the ICDC data-model contribution process and recorded in GitHub. The ticket points at the process (Section 1) and tracks the work; it does not restate the procedure, classify the version, or enumerate the schema artifacts.

**Pipeline, branch, & store anatomy (read this once before drafting)**

An ICDC model update touches multiple systems in sequence. Knowing the chain helps every section land:

- **Source-of-truth repo** — **`CBIIT/icdc-model-tool`** holds the canonical model definition. Two branches matter: **`develop`** (what Dev and QA serve) and **`master`** (what Stage and Prod serve, and what the downstream Data Hub tracks via tag). Model changes to `icdc-model-tool` promote by branch: the **`develop`** branch ties to the **Dev and QA** environments, and the **`master`** branch ties to the **Stage and Prod** environments. A model change lands on a feature branch, PRs into `develop` (making the new model version live in Dev and QA), then `develop` PRs into `master` (Stage and Prod) — two branch promotions cover all four environments. Note: this branch-based model promotion is distinct from **data loading** — a model version going live in a tier does not load any study's data there. Study data is loaded to each tier (Dev → QA → Stage → Prod) separately via the Data Loading Task; a model change that requires existing data to be re-loaded spawns a separate Data Loading Task.
- **Schema artifacts** — three files in `icdc-model-tool` must update together for a property/node change to be complete:
  - **`icdc-model.yml`** — node and relationship definitions. The `Version:` field at the top of this file is the canonical model version.
  - **`icdc-model-props.yml`** — property definitions (description, type, enum values, caDSR CDE binding, required vs preferred vs optional).
  - **`[ICDC-VERIFY — confirm the ICDC model version-history file]`** — what end users see in the Data Model Navigator's Version tab.
- **CDE source** — **caDSR**. New or updated CDEs and permissible values are requested via a **caDSR II Help Desk Request Form** (a ServiceNow-based ticket) to the caDSR/SI team. Assigned CDE codes are recorded in the CDE Request Workbook; the model's properties file carries the caDSR binding (or a `TBD` placeholder until codes are minted).
- **Loader repo** — **`CBIIT/icdc-dataloader`**. Python-based loader. Affected modules vary by change type: `data_loader.py`, `loader.py`, `file_loader.py`, `es_loader.py`, and `model-converter.py` (converts YAML schema to the GraphQL schema used by the frontend).
- **Frontend repos** — `[ICDC-VERIFY — ICDC frontend repo]` and related. Rendering changes when new fields need to be displayed.
- **Promotion mechanism** — **git + GitHub**, per the ICDC data-model contribution process `[ICDC-VERIFY — confirm ICDC's data-model contribution SOP/process]`. The model moves on feature branches and PRs (`develop` is validated on Dev/QA, `master` on Stage/Prod) and propagates downstream via a git tag and GitHub Release. There is **no data-loading Jenkins pipeline** in model contribution; a Jenkins load runs only when existing data must be re-loaded under the new schema, tracked separately as a Data Loading Task (the Data Loading Task template).
- **Graph database** — **Neo4j**. The canonical metadata store (the loader connects via `bolt://…:7687`). Model updates that add nodes or properties require a coordinated migration step before existing data can be reloaded under the new schema.
- **Search index** — **OpenSearch**. Reindex follows every load. If the schema change affects searchable fields, the index mapping may also need updating.
- **Downstream consumer** — `[ICDC-VERIFY — confirm whether ICDC's model syncs downstream to crdc-datahub-models]`. If ICDC mirrors the sibling-commons pattern, after tagging a release GitHub Actions would sync the new version into `crdc-datahub-models`, verified by inspecting `cache/content.json` on that downstream repo — whether ICDC has this downstream sync is unconfirmed.
- **Data Model Navigator** — the user-facing UI that displays the model at `caninecommons.cancer.gov`. Reads from the version-history file and the YAML files; updates flow automatically once the new version is in place.

**When to expand vs trim**

- **MINOR additive change, internally driven** (new optional property, new optional node, added enum value — e.g., internal Program/Portfolio curation properties) → use this template as-is. Verification (Section 5) is light. Section 2 (internal workbook) and the Section 3 DM Federal Lead & SME Review still apply; the caDSR II Help Desk Request Form row fills in only if a CDE/PV is added or changed.
- **PATCH change** (description fix, examples, metadata text) → use the template; expect Verification (Section 5) to focus on the Navigator's display. The DHDM review still happens; the caDSR II Help Desk Request Form row usually stays empty.
- **MAJOR change** (removed required property, type change, removed node, removed enum, tightened constraint) → the Modeling Summary states that existing data is unaffected until re-loaded; expect a separate Data Loading Task to follow with re-load of affected studies, linked via native Jira issue links.
- **Multi-property batched change** → one ticket per coherent change-set that ships as a single version bump. If changes are independent and could ship separately, use one ticket each.
- **Pure documentation update to `icdc-model-tool`** (README, owner guide, SOP edits) → this template is overkill. A free-form Task with the doc change description and a single PR link is enough.

**When NOT to use this template**

This template covers internally/ICDC-driven model changes across the full weight range. The following are different:

- **Study-driven model changes** — requested by an incoming study submission, anchored on that study's CDE Request Workbook. Use the **Data Modeling for Study Submission** template. The driver is the study, and the term-level truth lives in the study's workbook (owned by that study's Data Concierge), not the internal workbook.
- **Loading data into the existing schema** — new studies, new data added to existing studies, megazip loads. Use the **Data Loading Task** template. This is also where a breaking change's downstream re-load is tracked.
- **Software development that does not change the schema** — frontend features, backend refactors, microservice work, bug fixes, library upgrades. Use the software development family.
- **CRDC platform changes** — Fence, IndexD, Submission Portal upgrades owned by CRDC platform teams. Out of ICDC scope.
- **Bento Core MDF framework changes** — changes to the underlying MDF tooling itself (`bento-mdf` submodule). Upstream concern; file with the Bento team.

If a CRDC submission requires schema changes before it can be loaded, that's two pieces of data management work: a modeling ticket and a Data Loading Task, depending on each other but in separate tickets. If the change is requested by the study submission, the model work is a study-submission modeling ticket (the Data Modeling for Study Submission template, study workbook). If it is initiated by the ICDC project itself, the model work is an internally-driven Model Update Task (this template, internal workbook) regardless of whether it is additive or breaking.
